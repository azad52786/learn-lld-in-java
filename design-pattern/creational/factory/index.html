01 — Foundation

What is the Factory Pattern?

"

"Define an interface for creating an object, but let subclasses decide which class to instantiate. Factory Method lets a class defer instantiation to subclasses."

— Gang of Four (GoF), Design Patterns, 1994

🧠 In Plain English

Instead of writing new Dog() or new Cat() scattered all over your code, you ask a Factory to give you an animal — "give me a Dog" — and the factory handles the how. Your code only cares about the what, not the which concrete class.

💡
Core Idea — Replace new with a Factory call

Without Factory: Shape s = new Circle(); — client knows the concrete class.
With Factory: Shape s = ShapeFactory.create("circle"); — client only knows the interface.

Why Do We Need It?

Problem Without FactorySolution With Factory
Client code has new ConcreteClass() everywhere — tightly coupled Client depends only on the interface; factory handles instantiation
Adding a new type requires hunting every new call and updating it Add new type in one place — the factory. Client code unchanged.
Unit testing is hard — can't easily substitute a mock Inject a different factory in tests to return mocks
Business logic is mixed with object creation logic Creation is separated — Single Responsibility Principle satisfied

Java Simple Factory — Full Implementation 
// ── Step 1: Product Interface ──────────────────────────────────
public interface Shape {
    void draw();
}

// ── Step 2: Concrete Products ──────────────────────────────────
public class Circle implements Shape {
    @Override
    public void draw() { System.out.println("Drawing ⭕ Circle"); }
}

public class Rectangle implements Shape {
    @Override
    public void draw() { System.out.println("Drawing ▭ Rectangle"); }
}

public class Triangle implements Shape {
    @Override
    public void draw() { System.out.println("Drawing △ Triangle"); }
}

// ── Step 3: The Simple Factory ─────────────────────────────────
public class ShapeFactory {

    // static method — no need to instantiate the factory itself
    public static Shape create(String type) {
        return switch (type.toLowerCase()) {
            case "circle"    -> new Circle();
            case "rectangle" -> new Rectangle();
            case "triangle"  -> new Triangle();
            default         -> throw new IllegalArgumentException("Unknown shape: " + type);
        };
    }
}

// ── Step 4: Client ─────────────────────────────────────────────
public class Main {
    public static void main(String[] args) {
        Shape s1 = ShapeFactory.create("circle");     // Drawing ⭕ Circle
        Shape s2 = ShapeFactory.create("rectangle"); // Drawing ▭ Rectangle
        Shape s3 = ShapeFactory.create("triangle");  // Drawing △ Triangle
        s1.draw(); s2.draw(); s3.draw();
    }
}
⚠️
Limitation of Simple Factory

Every time you add a new shape, you must edit ShapeFactory — this violates the Open/Closed Principle (OCP). The factory grows into a big if/switch block over time. That's why Factory Method was invented.

Type Two — Official GoF

Factory Method Pattern

Define an abstract method in a base creator class. Each subclass overrides it to produce its specific product. The base class orchestrates the workflow — subclasses decide what to create.

Abstract Method Subclass decides type Open/Closed Principle Official GoF

Java Factory Method — Full Implementation (Notification System) 
// ── Step 1: Product Interface ──────────────────────────────────
public interface Channel {
    void send(String message);
}

// ── Step 2: Concrete Products ──────────────────────────────────
public class EmailChannel implements Channel {
    @Override
    public void send(String msg) { System.out.println("📧 Email: " + msg); }
}

public class SMSChannel implements Channel {
    @Override
    public void send(String msg) { System.out.println("📱 SMS: " + msg); }
}

public class PushChannel implements Channel {
    @Override
    public void send(String msg) { System.out.println("🔔 Push: " + msg); }
}

// ── Step 3: Abstract Creator ───────────────────────────────────
public abstract class Notifier {

    // ✅ THE Factory Method — subclasses must override this
    protected abstract Channel createChannel();

    // ✅ Template — uses the factory method internally
    // Client calls notify() — never worries about which Channel
    public void notify(String message) {
        Channel channel = createChannel(); // delegate to subclass
        channel.send(message);
    }
}

// ── Step 4: Concrete Creators ──────────────────────────────────
public class EmailNotifier extends Notifier {
    @Override
    protected Channel createChannel() {
        return new EmailChannel(); // ✅ subclass decides: Email
    }
}

public class SMSNotifier extends Notifier {
    @Override
    protected Channel createChannel() {
        return new SMSChannel(); // ✅ subclass decides: SMS
    }
}

public class PushNotifier extends Notifier {
    @Override
    protected Channel createChannel() {
        return new PushChannel(); // ✅ subclass decides: Push
    }
}

// ── Step 5: Client ─────────────────────────────────────────────
public class Main {
    public static void main(String[] args) {
        // ✅ Client works with the abstract Notifier — no concrete class names!
        Notifier n1 = new EmailNotifier();
        Notifier n2 = new SMSNotifier();
        Notifier n3 = new PushNotifier();

        n1.notify("Order confirmed!");  // 📧 Email: Order confirmed!
        n2.notify("OTP: 845231");       // 📱 SMS: OTP: 845231
        n3.notify("Your order shipped"); // 🔔 Push: Your order shipped
    }
}
✅
Key Advantage Over Simple Factory

Adding a new channel (e.g. WhatsAppNotifier) requires zero changes to existing classes. Just create a new subclass and override createChannel(). This fully satisfies the Open/Closed Principle.

⚠️
Limitation of Factory Method

Factory Method creates one type of product per factory. What if you need to create a whole family of related objects together — e.g. a Button + Checkbox + TextField all in the same OS theme? That's where Abstract Factory comes in.

03
Type Three — Official GoF

Abstract Factory Pattern

A factory of factories. Provides an interface for creating families of related or dependent objects — without specifying their concrete classes. Guarantees that products from the same family are always compatible.

Family of Objects Multiple Products Consistency Guaranteed Official GoF
🧠 Real World Analogy

Imagine a UI theme factory. You pick "Dark Theme" and get a DarkButton, DarkCheckbox, and DarkTextField — all matching. Or pick "Light Theme" and get all Light versions. The Abstract Factory ensures you never accidentally mix a DarkButton with a LightCheckbox.

Java Abstract Factory — Full Implementation (Cross-Platform UI) 
// ═══════════════════════════════════════════════════════════════
// STEP 1 — Abstract Products (what every family must provide)
// ═══════════════════════════════════════════════════════════════
public interface Button {
    void render();
    void onClick();
}

public interface Checkbox {
    void render();
    void onCheck();
}

// ═══════════════════════════════════════════════════════════════
// STEP 2 — Concrete Products — Windows Family
// ═══════════════════════════════════════════════════════════════
public class WindowsButton implements Button {
    @Override public void render()   { System.out.println("🪟 Rendering Windows Button"); }
    @Override public void onClick()  { System.out.println("🪟 Windows Button clicked"); }
}

public class WindowsCheckbox implements Checkbox {
    @Override public void render()   { System.out.println("🪟 Rendering Windows Checkbox"); }
    @Override public void onCheck()  { System.out.println("🪟 Windows Checkbox checked"); }
}

// Concrete Products — Mac Family
public class MacButton implements Button {
    @Override public void render()   { System.out.println("🍎 Rendering Mac Button"); }
    @Override public void onClick()  { System.out.println("🍎 Mac Button clicked"); }
}

public class MacCheckbox implements Checkbox {
    @Override public void render()   { System.out.println("🍎 Rendering Mac Checkbox"); }
    @Override public void onCheck()  { System.out.println("🍎 Mac Checkbox checked"); }
}

// ═══════════════════════════════════════════════════════════════
// STEP 3 — Abstract Factory Interface
// ═══════════════════════════════════════════════════════════════
public interface UIFactory {
    Button   createButton();
    Checkbox createCheckbox();
}

// ═══════════════════════════════════════════════════════════════
// STEP 4 — Concrete Factories (one per family)
// ═══════════════════════════════════════════════════════════════
public class WindowsFactory implements UIFactory {
    @Override
    public Button   createButton()   { return new WindowsButton(); }
    @Override
    public Checkbox createCheckbox() { return new WindowsCheckbox(); }
}

public class MacFactory implements UIFactory {
    @Override
    public Button   createButton()   { return new MacButton(); }
    @Override
    public Checkbox createCheckbox() { return new MacCheckbox(); }
}

// ═══════════════════════════════════════════════════════════════
// STEP 5 — Application (uses only interfaces, never concrete)
// ═══════════════════════════════════════════════════════════════
public class Application {

    private final Button   button;
    private final Checkbox checkbox;

    // ✅ Constructor receives a factory — never knows which OS
    public Application(UIFactory factory) {
        this.button   = factory.createButton();
        this.checkbox = factory.createCheckbox();
    }

    public void render() {
        button.render();
        checkbox.render();
    }
}

// ═══════════════════════════════════════════════════════════════
// STEP 6 — Main (picks the family based on OS / config)
// ═══════════════════════════════════════════════════════════════
public class Main {
    public static void main(String[] args) {
        String os = System.getProperty("os.name").toLowerCase();

        UIFactory factory = os.contains("mac")
            ? new MacFactory()
            : new WindowsFactory();

        Application app = new Application(factory);
        app.render();
        // On Mac:     🍎 Rendering Mac Button  +  🍎 Rendering Mac Checkbox
        // On Windows: 🪟 Rendering Windows Button + 🪟 Rendering Windows Checkbox
        // ✅ Guaranteed consistent — never mixes families
    }
}
✅
The Superpower of Abstract Factory — Family Consistency

The Application class has absolutely zero knowledge of Windows or Mac. It only speaks UIFactory, Button, Checkbox. Switch the entire UI from Windows to Mac by swapping one line in Main. Products are always compatible — you can never accidentally get a MacButton with a WindowsCheckbox.

07 — Watch Out

🚩 Bad Habits to Avoid

  • 🔨
    Using new ConcreteClass() directly in business logic The whole point of Factory is to remove new PayPalPayment() from your OrderService. If your service still has concrete class names, you haven't applied the pattern — you've just added a factory nobody calls.
  • 🏗️
    Turning Simple Factory into a God Class When your SimpleFactory has 50 cases and creates objects for 10 different systems, it becomes impossible to maintain. This is the signal to upgrade to Factory Method or Abstract Factory.
  • 🔀
    Mixing Factory Method with Simple Factory logic A common mistake: declaring createProduct() as abstract (Factory Method) but then also adding static if/switch in the base class. Pick one approach — don't hybrid them. It confuses readers and defeats the purpose.
  • 📦
    Using Abstract Factory when you only have one product type If you only create Button objects — not a family — Abstract Factory is overkill. Use Factory Method. Over-engineering with Abstract Factory for a single product type creates unnecessary interfaces and classes.
  • 🧩
    Products from different families being mixed accidentally When not using Abstract Factory, developers often mix products: a Windows Button with a Mac Checkbox. Abstract Factory exists precisely to prevent this. If consistency between related objects matters, always use Abstract Factory.
  • 🧪
    Hard-coding the factory selection in business logic Writing if (os.equals("windows")) new WindowsFactory() deep inside Application defeats the pattern. Factory selection belongs at the entry point (main or a config class) — not buried in business logic.
  • 🔍
    Not programming to the interface in the client Writing WindowsButton btn = factory.createButton() instead of Button btn = factory.createButton() immediately ties the client to a concrete type. Always use the product interface as the variable type.
🚨
The Golden Rule

If you see a concrete class name on the right side of = anywhere in your business logic (outside of factories and main), your factory pattern isn't working. All client code should only reference interfaces.
