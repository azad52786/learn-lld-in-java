01 — Definition

What is the Singleton Pattern?

"

"Ensure a class has only one instance, and provide a global point of access to it."

— Gang of Four (GoF), Design Patterns, 1994

🧠 In Plain English

No matter how many times you ask for the object, you always get back the same one. It's like the President of a country — there is only one at a time, and everyone refers to the same person. You cannot create a new one while the current one exists.

Thread A → getInstance()
→
Same Object
←
Thread B → getInstance()

↑ Multiple callers — always the same single instance returned.

02 — Why Use It

Why Do We Use Singleton?

Use CaseWithout SingletonWith Singleton
DB Connection Pool New pool created per request — memory explodes One shared pool reused across entire app
Logger Each class creates its own logger — inconsistent logs One logger instance writes all logs uniformly
App Config Config file read multiple times — wasteful and inconsistent Read once, shared everywhere as one instance
Thread Pool Multiple pools, threads not managed globally One pool manages all threads app-wide
Cache Multiple cache objects — stale, inconsistent data Single cache — all reads/writes go to one place
💡
The 3 Rules of Singleton

1. Private constructor — no one can call new MyClass() from outside.
2. Private static instance — the one object lives inside the class itself.
3. Public static getInstance() — the only way to get the object.

03 — All Implementation Types

🔨 Every Type of Singleton Implementation

There are 6 main ways to implement Singleton in Java — each with different trade-offs around thread safety, laziness, and simplicity. Know all of them for interviews.

① Eager Initialization
Simplest — instance created at class load time
⚡ Eager
✅ Thread Safe ❌ Not Lazy ✅ Simple ⚠️ Wastes memory if unused
Java EagerSingleton.java 
public class EagerSingleton {

    // ✅ Instance created when class is loaded by JVM
    private static final EagerSingleton instance = new EagerSingleton();

    // ✅ Private constructor — no one outside can call new
    private EagerSingleton() {}

    public static EagerSingleton getInstance() {
        return instance;
    }
}

// Usage
EagerSingleton obj1 = EagerSingleton.getInstance();
EagerSingleton obj2 = EagerSingleton.getInstance();
System.out.println(obj1 == obj2); // true — same object
⚠️
Problem with Eager

Instance is created even if it's never used during the app's lifetime. If the constructor is heavy (opens DB connection, reads files), this wastes resources.

② Lazy Initialization (Not Thread Safe)
Creates instance only when first needed — but BROKEN in multithreading
❌ Broken
❌ NOT Thread Safe ✅ Lazy ⚠️ Single-thread only
Java LazySingleton.java — ❌ NOT THREAD SAFE 
public class LazySingleton {

    private static LazySingleton instance; // null initially

    private LazySingleton() {}

    public static LazySingleton getInstance() {
        // ❌ DANGER: Two threads can both see null simultaneously!
        if (instance == null) {
            instance = new LazySingleton(); // ❌ Both threads create new objects!
        }
        return instance;
    }
}
🚨
Race Condition — The Bug

Thread A checks instance == null → true. Before A creates the object, Thread B also checks → also true. Both threads create a new instance. Now you have two objects. Singleton is broken. Never use this in production.

③ Thread-Safe with synchronized Method
Fixes thread safety — but every call locks, hurting performance
⚠️ Slow
✅ Thread Safe ✅ Lazy ⚠️ Performance bottleneck
Java SynchronizedSingleton.java 
public class SynchronizedSingleton {

    private static SynchronizedSingleton instance;

    private SynchronizedSingleton() {}

    // ✅ synchronized ensures only ONE thread enters at a time
    public static synchronized SynchronizedSingleton getInstance() {
        if (instance == null) {
            instance = new SynchronizedSingleton();
        }
        return instance;
    }
}
⚠️
Performance Problem

After the instance is created, synchronized is still acquired on every single call to getInstance(). Locking is expensive. In a high-throughput system this becomes a serious bottleneck. This is why Double-Checked Locking was invented.

④ Double-Checked Locking (DCL)
Best of both worlds — lazy + thread safe + fast
⭐ Recommended
✅ Thread Safe ✅ Lazy ✅ High Performance ⚠️ Needs volatile
Java DCLSingleton.java — ⭐ RECOMMENDED 
public class DCLSingleton {

    // ⚠️ volatile is CRITICAL — prevents instruction reordering by JVM
    private static volatile DCLSingleton instance;

    private DCLSingleton() {}

    public static DCLSingleton getInstance() {

        // 1st check — no locking needed if already created (fast path)
        if (instance == null) {

            synchronized (DCLSingleton.class) {

                // 2nd check — another thread may have created it while we waited
                if (instance == null) {
                    instance = new DCLSingleton();
                }
            }
        }
        return instance;
    }
}
✅
Why This Works — The Two Checks Explained

Check 1 (outside lock): Once instance is created, 99.9% of calls hit this and return immediately — no locking overhead at all.
Check 2 (inside lock): Handles the rare race at startup — ensures only one thread actually calls new.
volatile keyword: Prevents the JVM from reordering instructions during object construction — without it, another thread could see a half-constructed object.

⑤ Bill Pugh — Static Inner Class
Cleanest & most elegant — relies on JVM class loading guarantee
⭐ Most Elegant
✅ Thread Safe ✅ Lazy ✅ No synchronized needed ✅ No volatile needed
Java BillPughSingleton.java — ⭐ MOST ELEGANT 
public class BillPughSingleton {

    private BillPughSingleton() {}

    // ✅ Inner class is NOT loaded until getInstance() is called (lazy!)
    // ✅ JVM guarantees class loading is thread-safe (no synchronized needed!)
    private static class Holder {
        private static final BillPughSingleton INSTANCE = new BillPughSingleton();
    }

    public static BillPughSingleton getInstance() {
        return Holder.INSTANCE; // triggers Holder class load on first call
    }
}
✅
Why Bill Pugh is Brilliant

The Holder inner class is not loaded when BillPughSingleton loads — it's only loaded when getInstance() is first called. The JVM's class-loading mechanism is inherently thread-safe, so no synchronized or volatile is needed. Clean, fast, lazy, and thread-safe all at once.

⑥ Enum Singleton
Joshua Bloch's recommendation — serialization & reflection safe
🔒 Bulletproof
✅ Thread Safe ✅ Serialization Safe ✅ Reflection Safe ❌ Not Lazy (eager)
Java EnumSingleton.java — 🔒 REFLECTION & SERIALIZATION SAFE 
// ✅ The simplest and most bulletproof Singleton in Java
public enum EnumSingleton {
    INSTANCE; // ← that's it. This IS the singleton.

    public void doSomething() {
        System.out.println("Singleton via Enum!");
    }
}

// Usage
EnumSingleton.INSTANCE.doSomething();

// ✅ Reflection cannot break it — JVM prevents enum instantiation
// ✅ Serialization cannot create a second instance — JVM guarantees it
🔒
Why Enum is the Most Bulletproof

Other Singleton types can be broken by Reflection (Constructor.setAccessible(true)) or Serialization (deserializing creates a new instance). Enum is immune to both — the JVM itself prevents anyone from creating a second enum instance. Recommended by Joshua Bloch in Effective Java.

05 — Real World Example

🗄️ Database Connection Pool — Singleton in Action

The most classic real-world Singleton — a database connection pool. You never want multiple pools; they'd each hold separate connections, waste memory, and cause connection limit errors.

Java DatabasePool.java — Bill Pugh Singleton 
public class DatabasePool {

    private String connectionUrl;
    private int    poolSize;

    private DatabasePool() {
        // Simulate loading config and opening connections
        this.connectionUrl = "jdbc:mysql://localhost:3306/mydb";
        this.poolSize      = 10;
        System.out.println("✅ DB Pool initialised — " + poolSize + " connections");
    }

    private static class Holder {
        private static final DatabasePool INSTANCE = new DatabasePool();
    }

    public static DatabasePool getInstance() {
        return Holder.INSTANCE;
    }

    public String getConnection() {
        return "Connection from pool @ " + connectionUrl;
    }
}

// ── Usage anywhere in app ──────────────────────────────────────
public class OrderService {
    public void saveOrder(String order) {
        DatabasePool pool = DatabasePool.getInstance(); // same object every time
        String conn = pool.getConnection();
        System.out.println("Saving order using: " + conn);
    }
}

public class UserService {
    public void findUser(int id) {
        DatabasePool pool = DatabasePool.getInstance(); // same object — no new pool!
        String conn = pool.getConnection();
        System.out.println("Finding user using: " + conn);
    }
}
✅
Result

No matter how many services call DatabasePool.getInstance(), the constructor runs exactly once. All services share the same pool. No wasted connections, no inconsistent state.

06 — Watch Out

🚩 Bad Habits to Avoid

  • 🔓
    Forgetting volatile in DCL Double-Checked Locking without volatile is broken. The JVM can reorder instructions during object construction, letting another thread see a partially-constructed instance. Always pair DCL with volatile.
  • 🧵
    Using Lazy (non-synchronized) in multithreaded code The basic lazy singleton without synchronized will create multiple instances under concurrent load. This is the most common Singleton bug in real codebases.
  • 🔍
    Not protecting against Reflection attacks Using Constructor.setAccessible(true), anyone can break your Singleton and create a new instance. Only Enum Singleton is immune. For other types, add a guard in the private constructor: if (instance != null) throw new RuntimeException().
  • 📦
    Singleton for everything — overuse Singleton creates hidden global state. Overusing it makes code tightly coupled, hard to test (you can't inject a mock), and causes bugs that are difficult to reproduce. Use it only for truly shared, stateless or carefully managed resources.
  • 🧪
    Singleton is an anti-pattern for unit testing Because you can't inject a mock, Singleton makes unit tests depend on real external resources (real DB, real file system). Always expose the dependency through an interface alongside the Singleton to keep code testable.
  • 💾
    Forgetting serialization safety If your Singleton implements Serializable, deserializing it creates a brand new instance — breaking the contract. Add protected Object readResolve() { return getInstance(); } to fix this, or just use Enum Singleton.
  • 🏛️
    Storing mutable state in Singleton Since every thread shares the same instance, mutable state inside a Singleton can cause race conditions. Either make the Singleton immutable/stateless, or use proper synchronisation for every state-changing method.
💡
The Reflection Guard (add to any non-Enum Singleton)

Add this inside the private constructor to block reflection attacks:

Java Reflection-safe private constructor 
private MySingleton() {
    // Guard against reflection attack
    if (Holder.INSTANCE != null) {
        throw new RuntimeException("Use getInstance() — Singleton cannot be instantiated directly!");
    }
}
